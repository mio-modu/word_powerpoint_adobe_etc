# 단축키

**워드 키와 한글 키를 둘 다 받습니다.** 두 프로그램의 관례가 다른데 (가운데 정렬이
워드는 `Ctrl+E`, 한글은 `Ctrl+Shift+C`) 둘 다 걸어뒀습니다. 어느 쪽에서 오셨든
손에 익은 키가 그대로 먹습니다. 프로그램 안에서 **F1** 을 누르면 같은 목록이 나옵니다.

| 기능 | 키 | 출처 |
|---|---|---|
| 파일 열기 | `Ctrl+O` | 공통 |
| 저장 | `Ctrl+S` / `Alt+S` | 공통 / 한글 |

## 브라우저가 가져가는 키

웹페이지가 막을 수 없는 조합이 있습니다. 브라우저가 먼저 처리해 버립니다.

| 키 | 브라우저 동작 | 원래 쓰임 |
|---|---|---|
| `Ctrl+N` | 새 창 | 한글의 새 문서, **표 만들기 `Ctrl+N,T` 의 앞자리** |
| `Ctrl+T` | 새 탭 | |
| `Ctrl+W` | 탭 닫기 | 한글의 문서 닫기 |
| `Ctrl+Shift+T` | 닫은 탭 복원 | |
| `Ctrl+Shift+N` | 시크릿 창 | |

그래서 한글의 표 만들기 `Ctrl+N,T` 는 **`Ctrl+Alt+T`** 로 대체했습니다.
프로그램 안의 단축키 목록(F1)에도 "원래 Ctrl+N , T" 라고 함께 적어 둡니다.

**데스크톱 앱으로 감싸면 이 제약이 사라집니다.** 그때는 `Ctrl+N,T` 를 포함해
원래 키를 그대로 되돌릴 계획입니다. 연속 키(`Ctrl+N` 다음 `T`) 처리는 이미
구현해 뒀으니, 키 정의만 바꾸면 됩니다.

## 한글 입력 중의 처리

한글을 조합하는 중에는 단축키를 가로채지 않습니다. 가로채면 조합이 깨집니다.
또 한글 입력 상태에서는 키 이벤트가 자모(`ㅂ`)로 오는데, 물리 키 위치를 보고
영문 자판 기준(`q`)으로 되돌려 처리합니다. 한글 상태에서 `Ctrl+B` 를 눌러도
진하게가 먹는 이유입니다.
